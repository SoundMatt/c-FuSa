# ISO 26262 in c-FuSa

ISO 26262 (Road vehicles — Functional safety) is the primary standard c-FuSa targets: ASIL derivation (`cfusa hara asil`), hazard analysis (`cfusa hara`), and ASIL-scaled gates across several other commands. This page states plainly what is and isn't ASIL-scaled today, alongside the command mapping — mirroring [`do178c.md`](do178c.md)'s and [`misra-c.md`](misra-c.md)'s same-project honesty about scope.

**c-FuSa is not a certification product. It is an engineering accelerator** (see the top of the [README](../../README.md)). Nothing on this page is a substitute for an accredited safety assessment.

## Command mapping

| ISO 26262 Artefact | cfusa Command |
|---|---|
| Hazard Analysis and Risk Assessment (Part 3 Clause 6) | `cfusa hara init` / `cfusa hara show` |
| ASIL determination (Part 3 Table 4) | `cfusa hara asil --severity --exposure --controllability` |
| Part 6 objective gap report | `cfusa iso26262 --asil ASIL-A\|B\|C\|D` |
| HLR/LLR decomposition | `cfusa trace --strict-hlr-llr` |
| FMEA | `cfusa fmea` |
| TARA (ISO 21434, often paired with ISO 26262) | `cfusa tara` |
| Safety case (GSN) | `cfusa safety-case` |
| Structural coverage (Part 6 Table 12) | `cfusa coverage --asil QM\|ASIL-A\|B\|C\|D` |
| Cyclomatic complexity | `cfusa comp --asil-d\|c\|b\|a` (or automatic via `check`, see below) |
| Tool qualification / V&V independence (Part 8 §11) | `cfusa qualify --project-asil` |
| MISRA-C:2012 (commonly paired with ISO 26262) | `cfusa misra` — see [`misra-c.md`](misra-c.md) |

## ASIL derivation

`cfusa hara asil` implements ISO 26262-3:2018 Table 4 (the S×E×C severity/exposure/controllability derivation, with the C0 "controllable in general → QM" extension per §4.3.5) in `src/asil.c`'s `cfusa_compute_asil()` — the single shared implementation used by both `cfusa hara` and the `check` engine's HARA006 consistency rule, so both call sites are provably using the identical table. Exhaustively tested against all 27 reachable S×E×C cells.

## What scales by ASIL today

The following gates and reports read a declared ASIL (via `--asil`/`--project-asil`, or `iso26262:ASIL-X` in `.fusa.json`'s `standards[]`) and change behavior accordingly:

- **`cfusa iso26262`** — the Part 6 objective applicability matrix (e.g. "no recursion", "no dynamic memory allocation", coupling analysis) is gated to the ASIL levels each objective actually applies at, not a flat checklist.
- **`cfusa coverage --asil`** — ISO 26262-6 Table 12 structural-coverage requirements: ASIL-D requires MC/DC, ASIL-C requires full branch coverage, ASIL-A/B require full statement coverage, QM has no requirement.
- **`cfusa comp` / `check`'s automatic `COMP001`** — cyclomatic complexity threshold scales by declared ASIL (ASIL-D=4 … ASIL-A=20), whether invoked directly via `--asil-d/c/b/a` or picked up automatically from `.fusa.json` during `cfusa check`.
- **`cfusa qualify --project-asil`** — V&V independence is *computed* from `--implementation-author`/`--independent-reviewer`/`--independent-test-executor` (not accepted as free-text input) and *gated*: a project declaring ASIL-D with no demonstrated independent review/test fails the command, per ISO 26262-8 §11's actual intent.
- **`check`'s HARA005/HARA006`** — a hazard's ASIL may not exceed the project's declared ASIL (HARA005), and a hazard's stored ASIL must match what `cfusa_compute_asil()` derives from its own S/E/C rating (HARA006).
- **`cfusa misra`** — the accredited-third-party-tool recommendation escalates from a soft note to a stated hard requirement (`REQUIRED`, not `RECOMMENDED`) when ASIL-C/D is declared.

Where both a DO-178C DAL and an ISO 26262 ASIL are declared on the same project (`cfusa coverage`, `check`'s `COMP001`), **the stricter of the two requirements applies** — a project claiming both standards must satisfy whichever is more demanding, never the laxer one silently winning.

## What does not scale by ASIL

Stated explicitly rather than left to be discovered:

- **Tool Confidence Level (TCL, ISO 26262-8 Tables 4–5).** No command in c-FuSa determines a TCL from tool impact (TI) and tool error detection (TD) classifications, and nothing gates tool-qualification evidence requirements against a computed TCL. This is a known, open gap — not an oversight kept quiet. (The wider x-FuSa tool family doesn't have this yet either, as of this writing.)
- **MISRA-C completeness at production ASIL.** See [`misra-c.md`](misra-c.md): the built-in rule set is a pattern-based subset, explicitly insufficient on its own for a production ASIL-C/D compliance claim.
- **Everything upstream of a declared ASIL.** c-FuSa scales *gates* by an ASIL you tell it about (via `--asil`/`--project-asil`/`.fusa.json`). It does not derive, question, or audit whether that declared ASIL is itself correct for your system — that's `cfusa hara`'s job (the S×E×C derivation above), and ultimately a safety-engineering judgment call outside any tool's authority.

## Workflow

```bash
cfusa hara init --dir .   # writes .fusa-hara.json
cfusa hara asil --severity 3 --exposure 4 --controllability 3   # -> ASIL-D
cfusa hara show --format json --output HARA.json

cfusa iso26262 --asil ASIL-D --output ISO26262_GAP.md
cfusa trace --strict-hlr-llr

cfusa coverage --lcov coverage.info --asil ASIL-D --output COVERAGE.json
cfusa comp --asil-d --output COMPLEXITY.md
cfusa misra --output MISRA_GAP.md

cfusa qualify --implementation-author "A. Engineer" \
              --independent-reviewer "B. Reviewer" \
              --independent-test-executor "C. Tester" \
              --project-asil ASIL-D \
              --output QUALIFY.json

cfusa check --dir . --format sarif --output check.sarif
```
